# Entitlement writes locked down — 2026-09-14

A permissions gap on `public.profiles` let the client write its own
entitlement columns. Found while testing the live backend before the v7
cutover, fixed the same day, and verified closed.

## Fix

```sql
revoke insert, update on public.profiles from anon, authenticated;
grant  update (display_name) on public.profiles to authenticated;

drop policy user_owns_profile on public.profiles;
create policy user_reads_own_profile on public.profiles
  for select using (auth.uid() = id);
create policy user_renames_self on public.profiles
  for update using (auth.uid() = id) with check (auth.uid() = id);
```

Also pinned `search_path` on `stamp_changed_at`.

## Verified after

Run against production as the `authenticated` role with a real user's
claims, every write inside a transaction that was rolled back:

- writing any entitlement column → `42501: permission denied for table profiles`
- reading own entitlement → works
- renaming self → works
- another account's `user_data` rows visible → 0
- another account's profile visible → 0

Nothing legitimate lost: the row is created by `handle_new_user`, a
SECURITY DEFINER trigger, so no client needs INSERT; both clients only
SELECT; the Worker writes entitlements with the service key, which these
grants do not constrain.
