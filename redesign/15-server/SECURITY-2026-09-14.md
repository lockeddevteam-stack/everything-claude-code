# A signed-in person could make themselves Pro

Found while testing the live backend before the v7 cutover. Fixed the same
day. Written down because it was live, it was exploitable by anyone with an
account, and the fix changes what the database allows.

## What was wrong

`profiles` carries the entitlement — `subscription_status`, `current_plan`,
`plan_expires_at`, `trial_ends_at`. Two things lined up:

- the policy `user_owns_profile` was `FOR ALL` with `USING (auth.uid() = id)`
- `anon` and `authenticated` held `INSERT` and `UPDATE` on **every column**

So anybody with an account could send one request, with the publishable key
that ships in the client by design and their own session:

```
PATCH /rest/v1/profiles?id=eq.<their own id>
{"subscription_status":"active","current_plan":"annual",
 "plan_expires_at":"2099-01-01"}
```

and hold Pro forever. Nothing in either client did this, and nothing needed
to: the hole was in what the database permitted, not in what the app asked
for. Both the shipped app and the redesign only ever SELECT from `profiles`.

## Proven, not reasoned about

Run against the production database as the `authenticated` role carrying a
real user's claims, exactly as PostgREST would:

| | before | after |
|---|---|---|
| set own `subscription_status` to `active`, expiry 2099 | **succeeded** | `42501: permission denied for table profiles` |
| read own entitlement | works | works |
| rename self (`display_name`) | works | works |
| see another account's `user_data` rows | 0 | 0 |
| see another account's profile | 0 | 0 |

The "before" write was rolled back.

## The fix

```sql
revoke insert, update on public.profiles from anon, authenticated;
grant  update (display_name) on public.profiles to authenticated;

drop policy user_owns_profile on public.profiles;
create policy user_reads_own_profile on public.profiles
  for select using (auth.uid() = id);
create policy user_renames_self on public.profiles
  for update using (auth.uid() = id) with check (auth.uid() = id);
```

Nothing legitimate lost. The row is created by `handle_new_user`, a SECURITY
DEFINER trigger on `auth.users`, so no client needs INSERT. The Worker writes
entitlements with the service key, which these grants do not constrain.
`display_name` stays the person's to set; everything that decides what they
have paid for is the server's.

## Also fixed

`stamp_changed_at`, the trigger added this session, was created without a
fixed `search_path` and the linter flagged it. Now
`SET search_path = public, pg_temp`. Nothing in it was unqualified; pinning
cost nothing.

## Still open, and it needs the dashboard

**Leaked password protection is off.** Supabase can refuse passwords found in
the HaveIBeenPwned corpus; it is a switch under Auth → Policies and cannot be
set from SQL or the API. Worth turning on before a wider launch.

## One mistake of mine, recorded

While testing the fix I used a `DO` block with `RAISE NOTICE`, whose output
this tooling does not return — so I saw nothing, and the block had committed.
It set one real account's `display_name` to "Renamed By Themselves". I caught
it on the next read, established the original value was NULL (every other
account is NULL, `handle_new_user` writes only `id` and `email`, and no
client writes the column), and restored it. Entitlements were untouched: that
write had already been refused, which is how the fix was confirmed working.
Every later test ran inside an explicit transaction with `rollback`.
